# Security review, 2026-10-24: `release-prep` before release 1.0

Read-only review of `src/` and `tools/build.sh` at `release-prep` (7878e02,
the slimmed code of `docs/reviews/slim-2026-10-24-brief.md`). Every release
file was read whole: `hue_bridge/driver.lua` and `driver.xml`,
`bridge/*.lua`, `common/log.lua`, `common/dispatch.lua`, `common/device.lua`,
`hue_light/driver.lua`, `light/*.lua`, `hue_scene/driver.lua` and both device
`driver.xml`; then the dev-only files (`common/devloop.lua`,
`bridge/devtools.lua`, `bridge/conntest.lua`, `bridge/pinning.lua`) and the
network surface of `tools/devserver.py`; then the branch diff against `main`
for every file the slimming touched, checked item by item against
`docs/code-analysis-2026-10-22.md`. Nothing was built or run and nothing was
sent to the controller or the bridge; the artefact checks (22 actions, no
dev files in the `.c4z`) stay with `docs/release-checklist.md` §0. Line
numbers are those of 7878e02.

## Verdict

No high or critical finding in the release build. Every TLS connection a
release driver makes verifies the peer against the two Signify roots shipped
in the archive, the only `ssl_*` options in release code
(`bridge/http.lua:34-36`); the insecure and system-CA modes are gone from
`http.lua` and live only in the dev-only `conntest.lua`. The application key
is written encrypted, read once at startup, and reaches nothing but the
`hue-application-key` header; no log line, property, list item or
inter-driver message carries it. No string from the bridge or from Composer
is used as a Lua pattern or a format string. The development loop and the
diagnostic handlers are absent from a release build by file removal, by
`require` guards and by an XML strip, and two specs pin the guards. The one
item worth fixing before the release is the bridge identity check on the
normal path (finding 1): a cheap change that closes the only path by which
the key can reach a host other than the paired bridge. Everything else is
low-severity hardening or dev-build-only exposure that the dev-loop design
already names.

## Release build: the development surface is absent

Verified by reading (the brief forbade a build; `docs/release-checklist.md`
§0 checks the artefact):

- `tools/build.sh:48-54`: a build without `--dev` removes
  `common/devloop.lua`, `bridge/devtools.lua`, `bridge/conntest.lua` and
  `bridge/pinning.lua` from the stage and strips both `DEV-ONLY` blocks of
  `hue_bridge/driver.xml` (`:133-147`, the `Diagnostic Server` and `Dev
  Server` properties; `:377-406`, the `Connection Test`, `Reload
  Credentials` and `Check CA Pinning` actions). The device `driver.xml`
  files have no such block. The awk drops the marker lines themselves.
- `tools/build.sh:23`: dp3's `--allowexecute` (Composer's Lua command
  window) only with `--dev`.
- `hue_bridge/driver.lua:23-40`: `common.devloop` is `pcall(require)`d;
  `bridge.devtools` is required only when that succeeded. Every development
  handler (`Dev Server`, `Hue Request`, the four probes, `HUE_LOG`, `Proxy
  Command`, `Lights Report`, `Reload Credentials`, `Check CA Pinning`,
  `Connection Test`, `Test Connection` with `Host`) is registered in
  `devtools.install` (`devtools.lua:404-420`) and nowhere else (grep of
  `src/`). The release `Test Connection` (`driver.lua:710-712`) uses
  `state.ip` only. The scene driver's `HUE_DUMP` no longer exists.
- `common/device.lua:122-144`: `DEV_RELOAD` and the log forwarding exist
  only when `common.devloop` loads; release builds leave `log.sink` alone.
- No other `require` of the four modules exists in `src/`; the only
  `loadstring`/`load` in `src/` is `devloop.lua:87`.
- Specs pin the guards: `tests/spec/drivers_spec.lua:314` (no development
  handlers and no `bridge.devtools` without `common.devloop`),
  `tests/spec/device_spec.lua:77` (no `DEV_RELOAD`, `log.sink` untouched).
- The `Dev Server` value a dev build left in the project is inert in a
  release build: no property handler reads it (`docs/dev-loop.md` notes the
  value survives, which is the intended way back to the loop).

"Checked and found sound" on 2026-10-22, re-confirmed now: the key encrypted
at rest and never logged (`credentials.lua:25`, `:46-55`; `http.lua` logs the
URL and body, never the headers); no untrusted string as a pattern or format
(the only non-literal `string.format` first argument is `conntest.lua:59`,
fed literals; the only built pattern is `devloop.lua:740-743`, from the
literal prefix); URLs from validated addresses (`config.parse_ipv4`,
`altaddr` spellings derived from it); TLS insecure mode now only in the dev
module `conntest.lua:31`, `http.lua` has none; stream timers
generation-gated; command queue bounded and timer-safe; registry invariants
against double adoption; project callbacks pcall-wrapped (`project.lua:52-59`,
`lights.lua:497-504`); device timers cancelled on unbind, forget and destroy
(`hue_light/driver.lua:910-916`, `hue_scene/driver.lua:1391-1398`,
`device.lua:433-438`); a release build cannot enable the dev loop.

The CA bundle `src/hue_bridge/certs/hue_ca_bundle.pem` holds exactly two
self-signed roots, `C=NL, O=Philips Hue, CN=root-bridge` and `C=NL, O=Signify
Hue, CN=Hue Root CA 01` (checked with openssl), generated by
`tools/gen_ca_bundle.sh` from the two PEMs beside it. No LAN address of the
house, no application key and no private key is in the working tree of
`src/`, `tools/`, `tests/` or `docs/` (grep; the git history point is
`docs/licensing-research.md` P1-P3 and out of this review's scope).

## Residual risks accepted by design

- Hostname verification is off for the bridge; the compensating check is
  finding 1.
- Pinning depends on OS 3.4.2's handling of a relative `ssl_cabundle`
  (`http.lua:8-13`). On another OS release the option might be ignored
  rather than fail; it fails closed on this one. `Check CA Pinning` (dev
  builds) is the way to re-verify after a controller upgrade.
- Inter-driver messages trust the project (finding 9).
- Composer property values and dynamic-list rows are visible to anyone with
  Composer access; none of them is a secret (bridge id and address are not).
- `Stream Watchdog (s)` is declared with minimum 0 while the code treats
  anything below 60 as 60 (`docs/status.md` notes it).

## What to fix before 1.0

Finding 1 (the identity comparison in `choose_stream_address`, with the
single-queue path included), a few lines next to code that already does it
in `test_connection`, plus one spec. Findings 2, 3 and 12 are the next
cheapest and can follow in the same change or after the release; the rest is
hardening of the same weight as the open items of 2026-10-22. The dev-build
findings (13-15) need no change for the release, since the code is not in
it, but should be the first thing done when the dev loop is next installed
on the house.
