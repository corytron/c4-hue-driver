# Security review of the driver source, 2026-11-13 (#480)

The merged result of the review under
[`security-review-design.md`](../security-review-design.md). Four
reviewers read all four drivers' source with the emphasis the owner asked
for: running on, and installing on, a Control4 controller. Their full
reports are beside this file:
- network trust: [`security-2026-11-13-network.md`](security-2026-11-13-network.md);
- the bridge driver's controller surface: [`security-2026-11-13-controller.md`](security-2026-11-13-controller.md);
- the device drivers: [`security-2026-11-13-devices.md`](security-2026-11-13-devices.md);
- install and supply chain: `security-2026-11-13-install.md`, published once the dev key is retired.

## Summary

- **No Critical and no High finding.**
- **Two Medium**, both on the development and release path, not in a
  release driver's runtime:
  - development packages carrying the dev key were served to the LAN
    during installs (I-1);
  - `deploy.py` does not tie a release's provenance to `main` (I-2).
- **Seventeen Low and thirteen Info.** Most need a hostile driver already
  installed in the same Control4 project, a hostile host on the LAN, or a
  rooted Hue bridge.
- **What holds:**
  - a release build keeps nothing that compiles or runs Lua it receives;
  - the application key never appears in a property, a list row or a log
    line;
  - every format string is a literal;
  - the driver changes no Hue automation without the owner's click;
  - the TLS identity check and the key's handling hold, apart from N-5;
  - every earlier fix holds, except 2026-10-24 #2 (the event-stream cap,
    N-1) and 2026-10-25 #9 (the dev handlers, C-2), which have partly
    regressed.
- **Contained the same day (I-1):** every local package carrying the dev
  key was deleted, and no install server is running. The house runs a
  release, with no dev build installed. Retiring the key is left to the
  owner.
