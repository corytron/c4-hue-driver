# Licensing research: making c4-hue-driver public

Research note, 2026-10-24, branch `release-prep`. Read-only; nothing in the
repository was changed. Every statement is marked **[verified: source, read
2026-10-24]** or **[assumed]**. Quotes are kept to a sentence. This is research,
not legal advice; the owner decides whether to publish (CLAUDE.md, "Licensing").

Owner's four requirements: (1) not run afoul of Control4/Snap One or Signify,
(2) not expose us legally, (3) as open as possible, (4) allow forking.

## 2. Snap One / Control4

- **The SDK documentation's license.** `LICENSE.md` of `snap-one/docs-driverworks-api`, `docs-driverworks-fundamentals`, `docs-driverworks-proxyprotocol-lightv2`, `drivers-common-public`, `drivers-driverpackager` is the same proprietary text [verified: local clones under `~/c4-tools`, and https://github.com/snap-one/drivers-common-public/blob/master/LICENSE.md]: "use without a valid license from Control4 is strictly prohibited"; the user "shall keep all content contained herein confidential"; "No part of this publication may be reproduced … without the express written consent of the publisher"; and any "Derivative Work" of their code "shall be owned by Wirepath Home Systems, LLC". GitHub classifies all of them, and `drivers-template-code-public`, as license "Other / NOASSERTION" [verified: GitHub API for the four repos]. The DriverWorks home page says "Use of them requires signing Control4's SDK License Agreement" and gives busdev@control4.com [verified: https://github.com/snap-one/docs-driverworks]. The agreement itself is not public **[assumed]**; whether the owner has signed one is a question for the owner.
- **Consequences for this repo.** Nothing of theirs may be copied in (code, doc passages, logo). Using the published API (function names, proxy command names, `driver.xml` schema) to write an independent driver is what the SDK exists for and is not expression Snap One can license away **[assumed: general US copyright law; interface facts]**. The eight quoted sentences (§1) are the only copies; remove them.
- **Is publishing a third-party driver restricted?** No public text says so. Snap One's own guideline says "our open platform gives manufacturers and driver developers several ways to integrate with Control4" and lets "driver developers … utilize the Connects with Control4 badge" subject to its rules [verified: https://docs.control4.com/docs/product/control4/connects-with-control4-guidelines/english/revision/A, pp. 1-3]; the packager README documents a GitHub Action for building `.c4z` files in users' own repositories [verified: README in the local clone]. Community-published drivers exist [verified thread exists, content not vetted: https://www.c4forums.com/forums/topic/20604-open-source-drivers-available/]. **[assumed]**: publishing is fine; selling through Snap One's channels would need their programs.
- **Trademarks.** "Control4 and the Control4 logo and DriverWorks are trademarks or registered trademarks of Wirepath Home Systems, LLC" [verified: the LICENSE.md above, 2020 text]; current notices read "Snap One and its respective logos are registered trademarks or trademarks of Snap One, LLC" with Control4 in the list [verified: https://help.snapone.com/c4-ds2-qs/Content/Template%20Topics/Landing.htm, © 2026]. The "Connects with Control4" badge "is unique artwork and a trademark of Control4. Never alter the logo in any way" [verified: guideline PDF p. 3]. So: no logo, no badge, no "Control4 Certified" wording; the plain word "Control4" to say what the driver runs on is nominative use **[assumed]**; attribute it (§5). The pairing `devicetype` is `control4#hue_bridge` (`src/hue_bridge/bridge/pairing.lua:21`) [verified]: the Hue bridge's whitelist will show the app as "control4", which reads as Snap One's own app; rename to `c4-hue-driver#bridge` for new pairings (existing keys keep their recorded name; no re-pair needed) **[assumed: devicetype is recorded at key creation only]**.

## 3. Signify / Philips Hue

- **Hue Developer Program Terms**, "Version: September 2025", readable without login [verified: https://developers.meethue.com/terms-of-use-and-conditions/]. Points that matter:
  - §2 grants "a limited, revocable, non-transferable, non-exclusive (without the right to sublicense) right … to create a product, app or service that operates with the Hue bridge." The license sits with the developer account; the owner should hold a Hue developer account that accepted these terms **[assumed: the owner registered to read the login-walled pages]**. The driver's users create their own keys on their own bridges (link button, `pairing.lua`), so no key or shared credential is distributed, and the key is stored encrypted and never shown in a property [verified: `src/hue_bridge/bridge/credentials.lua` header].
  - §8(a)(v): do not "republish, reproduce, distribute, display, post or transmit any part of the API Content" ("the Hue API(s), Hue account for this site, and Hue developer materials"); §8(a)(vi) forbids derivative works of API Content "except for the sample code provided". Hence: no copies of the login-walled documentation in the repo (none found, §1); the certificates are the one grey item (§1).
  - §6: "Signify limits the number of remote API calls. The limit is currently set to a total of 50000 calls per day" — the **remote** (cloud) API, which this driver does not use. Local-API guidance (about 10 light commands/s and 1 grouped_light command/s, the stream's 1 s batching) is on the login-walled "Hue System Performance" page [verified: login page returned]; the numbers in `commands.lua` come from the owner's read of it on 2026-10-19 (commit 08f85b3) **[assumed here]**. Numbers are facts and may stay in comments.
  - §7 API Content "as is"; §16 Signify "will not be liable for any damages"; §12 termination on breach or six months without (remote) traffic; §17 Dutch law, Amsterdam courts; "Some of the software required by or included in the API Content may be offered under an open source license." Nothing forbids open-sourcing a client.
  - §8(a)(xi), the naming clause: do not "use any Philips Hue, Hue or Signify branding, trademarks or trade dress … in any logo or graphics", **but** a developer of a compatible app may "(A) use 'works with Philips Hue' and 'for Philips Hue' solely in your product-related material for the app; and (B) name your app such that it includes the word 'Hue' in combination with other purely descriptive words, provided that you do not create a unitary name/mark incorporating the 'Hue'."
- **Philips marks** (the "Philips" half of "Philips Hue") belong to Koninklijke Philips N.V.; its guidelines (April 2024) require written authorisation for Philips marks and brand assets, allow saying a product is "compatible with" or "works with" a Philips product, forbid suggesting "any affiliation, endorsement or sponsorship", and forbid "the Philips name or the Philips Trademarks in combination with or as part of your trade name", domain or app name [verified: https://www.philips.com/a-w/about/innovation/ips/philips-general-trademark-use-guidelines.html]. HUE-formative marks (HUE, WORKS WITH HUE, FRIENDS OF HUE) are filed by Signify Holding B.V. [verified owner listing, registration status not checked: https://trademarks.justia.com/owners/signify-holding-b-v-4123996].
- **Applied to this project.** `Hue Light`, `Hue Scene` = "Hue" + descriptive word: allowed by (B). `Hue Bridge` is also the product's own name; as a Composer device name it names the hardware the driver controls, exactly as "Apple TV", "Sonos Network" and "August Gateway" appear in the same tree [verified: `tree-bridge.png`], and the model text `Hue Bridge (CLIP v2)` and `<creator>Cory Fair</creator>` already separate authorship from the device. Keep the three display names and the `hue_*.c4z` file names **[assumed acceptable]**; do not name the repo or any artefact "Philips …"; keep `<manufacturer>Philips Hue</manufacturer>` because in Composer that field describes the controlled device's maker, not the driver's author **[verified: Composer's search lists Control4's own Hue driver the same way, `documentation.html:128`; legal reading assumed]**. Say "works with Philips Hue" or "for Philips Hue" in README and manuals, never "official", never a Hue logo, and add the non-affiliation sentence everywhere a user reads (README, three manuals, `driver.xml` description). Icons: see §1.

## 5. License recommendation

| Requirement | MIT | BSD-3-Clause | **Apache-2.0** | MPL-2.0 |
|---|---|---|---|---|
| As open as possible, forkable | Yes | Yes | Yes | Weak copyleft: modified files must stay MPL and ship source [verified: https://choosealicense.com/licenses/mpl-2.0/] |
| Patent grant | None (silent) | None | Explicit, §3, with termination on patent suits | Explicit, §2.1(b) |
| Trademark handling | Silent | §3: names of holder/contributors not to "endorse or promote products derived from this software without specific prior written permission" [verified: https://choosealicense.com/licenses/bsd-3-clause/] | §6: "This License does not grant permission to use the trade names, trademarks, service marks, or product names of the Licensor …" [verified: https://www.apache.org/licenses/LICENSE-2.0] | §2.3: no trademark rights **[assumed from memory of the text]** |
| Contributions | Nothing said | Nothing said | §5: contributions "shall be under the terms and conditions of this License, without any additional terms" (no CLA needed) | Contributions are MPL by definition |
| Warranty / liability | One short paragraph [verified: https://choosealicense.com/licenses/mit/] | Same | Detailed §7-§8, plus §9 (anyone offering paid support indemnifies the authors) | Detailed §6-§7 |
| Fit | 3/4 (no patent or trademark language) | 3.5/4 | **4/4** | 3/4 (fails "as open as possible") |

**Recommendation: Apache License 2.0.** It is permissive and fork-friendly (requirements 3 and 4), says in the license itself that no trademark permission is granted (which keeps "Hue" and "Control4" out of the grant and protects the project's own name; requirement 1), carries the strongest disclaimers and a patent grant/termination (requirement 2), and settles contribution terms without paperwork. Trade-offs: longer text; Lua-ecosystem habit is MIT; GPLv2-only incompatibility (irrelevant here). If the owner prefers the shortest possible text, BSD-3-Clause is the runner-up; MIT third.
